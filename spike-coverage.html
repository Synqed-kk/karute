🗄️Schema (the big divergence)

spike: Part 3 of INTEGRATION_GUIDE.md, docs/SUPABASE_SCHEMA_PROPOSAL.md
🦊
Liam
Domain tables (customer, karute, recording, booking, etc.) live in Supabase Postgres with RLS policies enforcing tenant + role isolation. App talks to Supabase directly via JS client.
🍣
Anthony
All domain tables moved to synqed-core (Hono + Prisma + Postgres on Supabase). Karute talks to synqed-core over HTTP via @synqed-kk/client SDK. Supabase retained only for Auth + Storage.
📝
Why diverged: single source of truth for domain logic, easier multi-tenant enforcement (server-side x-business-id), and lets a future second client (web admin? mobile app?) reuse the same API without re-implementing RLS in client code. RLS is still active in Supabase for the residual auth/profile tables.
✦ diverged net win — keeps Supabase pluggable, centralizes business logic

🛡️AI rate limiting

spike: docs/SECURITY_HARDENING.md → "Per-org limits"
🦊

🪞Staff coaching system (Layer 1/2/3)

spike: INTEGRATION_GUIDE §11 — "Three layers of data"
🦊
Liam
The 3-layer privacy model: L1 staff-private (raw transcripts, in-session coaching), L2 owner-visible aggregates (closing rate, trajectory score, top-performer patterns anonymized for staff), L3 owner actions (assign learning modules, edit policies). Owner never reads L1 even via join. This is the core of the feature — violating it kills trust.
🍣
Anthony
Not built yet. Per-customer recording consent is shipped, but the per-staff coaching consent log + L1/L2/L3 split + learning modules + top-performer pattern catalog are all post-pilot.
🌱
Pilot is owner-only (no other staff at the test spa yet), so L1/L2/L3 separation isn't load-bearing on day 1. We can ship this when staff #2 onboards.
🌱 deferred unblocked when pilot adds a 2nd stylist
